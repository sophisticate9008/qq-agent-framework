## 发现与修正

| 缺陷 | 修正 | 安全语义与限制 |
| --- | --- | --- |
| 每次事件扫描所有功能 | 安装事务成功后发布订阅索引，卸载删除引用 | 不相关功能数量不再线性影响匹配；安装失败不泄露订阅 |
| 每次解析复制/排序所有偏好 | 作用域及持久/临时双层索引 | 仍按层级和成功更新时间覆盖；每次检查时效，不缓存动态结果 |
| 同作用域大量覆盖仍反复深复制来源 | 中间来源只在局部构造，最终公开快照统一复制冻结 | 新增深层冻结、旧快照不变回归；没有返回内部可变引用 |
| 每个副作用扫描所有授权 | feature/conversation/capability精确索引 | 保持授权插入顺序、耗尽/无权限区别、执行前重检与不退款 |
| 连续立即完成的事件饿死事件循环 | 默认每64次调度或累计8ms协作式让出 | 软预算，不能抢占一次同步处理器，不是硬实时保障 |
| 未使用状态仍为每个会话建立空命名空间 | 第一次访问状态时才取私有作用域 | 已写/读取的状态仍需生命周期治理，不声称所有状态有界 |
| 已完成副作用Promise留到处理器结束 | 结算后立即移出待处理集合，另留失败标志 | 处理器捕获失败也不能伪报完成；已启动动作仍排空 |
| 慢对端堵住全部出站 | 可选宿主并发槽位与同会话FIFO | 默认仍全局顺序；显式启用后才并行，等待后重检撤销 |
| 只看计数也深复制完整管理快照 | 增加轻量 engine.metrics() | 不含业务值；它不是完整快照的等价替代 |
| 静态页面重复读取文件 | 每服务器独立、合并在途读取的静态缓存 | 只限3个白名单文件，每个最多256KiB；失败/超大不保留；动态快照不缓存 |

保留了中间阶段测量：仅加索引时，同作用域10000条偏好的候选p95仍约26ms；
主线程复核发现多余的中间来源复制，修改后重新跑三轮context与core，最终数值如下。
本机 `summary-indexed-only.json` 留档，不把中间结果混为最终结果。

## 方法与最终观测

Node v24.22.1、Linux arm64、共享主机；系统报告可用并行度8，但CPU型号不可读。
同一套TS脚本以 BENCH_ROOT 切换基线/候选，每轮新进程；三轮交替先后顺序，中位数汇总。
每行p95是三次独立运行p95的中位数，不是合并全部样本后的p95；完整p50/p99、各轮吞吐、
CPU和内存读数在结构化证据中。没有统计显著性或生产SLA主张。

### 公平性、慢对端与过载

- 2000个立即完成事件期间，5ms定时器三轮从 `[0,0,0]` 次变为 `[32,31,31]` 次。
  这证明该负载下不再全程饿死定时器，不证明每次事件循环延迟低于8ms。
- 模拟一个80ms慢发送：另一个会话默认仍等待约81.5ms；显式并发4时中位等待约1.12ms。
  同会话顺序、总并发上限、排队后撤销不发出与槽位释放均有回归。
- 突发300事件：接受256、明确拒绝44，错误为 EVENT_BACKPRESSURE；
  不是把排队上限误写成“300个全部处理成功”。
- 1000功能+500审计的完整describe约82次/s，轻量metrics约94768次/s。
  两者返回内容不同，不用此比值宣传同操作加速；高频观测应取计数，大快照后续要分页/增量化。

### 短浸泡，不是长稳

预热500事件后，三窗口各4000个新会话，共12000个；显式GC在计时窗外。
基线空状态命名空间随窗口增长为4001/8001/12001，堆相对预热增长约0.98/1.98/3.07MB。
候选各窗口均为0个空状态命名空间，堆增量约9.8/29.7/13.7KB，事件/审计各保留128，队列归零。

候选RSS仍从约79.7MB升到105.4MB，不能称为“内存不增长”。RSS、GC后JS堆和业务保留对象
分别记录；基线RSS亦增长。本轮只有秒级窗口，不是小时/天级泄漏证明，且没覆盖持续写业务状态。
